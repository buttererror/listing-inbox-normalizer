# Phase 03 — Independent provider evaluation

**Status — Proposed plan, 2026-11-10.** Phase 02's CLI processing tasks are recorded complete; the [roadmap](../roadmap.md) still calls this phase a candidate. This plan defines work and exit checks, not evaluation results or provider qualification. [D-036](../DECISIONS.md#d-036-use-a-frozen-independent-corpus-and-separate-live-measurement) proposes the consequential evaluation protocol; approve it before running or publishing a qualification result.

## Goal and boundaries

Measure how the integrated, tool-less Gemini CLI performs on messages that did not guide its prompt or implementation. Keep the evaluator outside the runtime pipeline, use the public JSONL result as the primary scored output, and retain offline tests as separate behavior evidence. Phase 04 owns SQLite, HTTP and approval; Phase 05 owns stored-property duplicate matching. `duplicate_of: null` is expected in this phase and is not a deduplication score. Anthropic, OpenAI and `agy` are configured alternatives, but live qualification of each requires an explicit provider-specific run and report; Gemini is the primary Phase 03 target under D-024.

**Governing sources:** [Plan v2](../../PLAN-v2.md), [architecture](../architecture.md), [brief](../task-brief.md), [processing policy](../processing-resolution-policy.md), D-019, D-020, D-023, D-024, D-026, D-033 and proposed D-036. **Criteria:** SC-06–09, SC-11–14 and PC-03; check SC-12 as evidence toward generalization, never as proof about an unavailable hidden set.

## Proposed scoring contract

- A message's classification and source-ordered `detected_classes` are scored against the label. Count missing and extra intents separately.
- Match each expected offer to one output offer by labeled source association. Report missing, extra and wrong-associated offers; do not let a correct field on the wrong property count as correct.
- Compare each applicable field only after offer matching. Report correct value, wrong value, unsupported value accepted, supported value missed, and appropriate null. Public price comparisons include amount, currency and period; assess the internal price role through its effect on selection and review, if diagnostic capture is available. Distinguish inapplicable fields from missing fields.
- Compare review at both listing and reason-category levels. A listing that should be reviewed but is not is a false negative. Record human-readable reason quality separately from stable codes.
- Keep provider/invalid-extraction failures and unscored disputed labels in their own counts. Publish numerator and denominator for every rate and avoid a single blended quality score.

These details are the recommended protocol in D-036; they become binding for qualification only after approval. The corpus size and any minimum pass thresholds are deliberately unset. Establish them before the live baseline, with rationale tied to the assessment brief and available evaluation budget. Do not claim hidden-set performance from this corpus.

## Phase exit and evidence

Exit requires a frozen independent corpus and label audit, an evaluator with focused offline checks, one complete live Gemini run through the built CLI, reproducible scoring with audited mismatches, measured latency and usage or a precise account of unavailable metrics, a README report, and dated success-criteria and AI-log updates. Record the exact run manifest, commands, artifact paths, counts, denominators, case-level failures, model/configuration, and limitations here when work happens. Provider qualification and Phase 03 verification are separate judgments; a completed evaluation may reveal gaps that need correction or an explicit documented limitation.
