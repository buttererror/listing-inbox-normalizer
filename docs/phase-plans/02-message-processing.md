## Implementation order

Start with 02.0. Review the current prompt, schemas, pipeline, and tests against the single-sale baseline. Pair the typed contract and prompt with mocked examples in 02.1 before replacing downstream consumers. Reuse the existing gateway and source checks, switch Listings to validated typed candidates, and integrate through the existing processor. Use the approved policy rules directly in the affected stages.

After 02.0, wire each changed stage into the shared CLI flow as part of its task. In 02.1, connect the typed extraction envelope to the existing processor for a supported sale fixture, making only the downstream changes required to keep that slice runnable. Expand that path in the following tasks. 02.6 closes out full integration and regression coverage.

## Acceptance cases

- **02.0 / 02.0T — Stage 1.** Reuse the verified offline single-sale CLI path and existing gateway interface. Verify adapter request handling, structured responses, and typed provider failures offline. Verify authentication, a tool-free request, and a structured result through the real CLI using a controlled synthetic sale fixture. Apply the tool-less boundary in D-024. Workflows executing tools on untrusted input require verified isolation. Surface an unmet provider gate as a blocker and review any replacement separately.

- **02.1 / 02.1T — Stage 1.** Verify the gateway receives the untouched source text, a schema derived from Zod, and the [nine instructions in execution order](../architecture.md#stage-1--llm-classification--extraction), including association between segmentation and extraction. Check the full [classification matrix](../processing-resolution-policy.md#classification-policy), base classes in source order, no duplicate detected classes, ignored incidental greetings, and multiple offers within one class. Exercise candidate types for every extractable public field, including sale and rent, qualified prices, area kinds, and normalized Saudi phones.
- **02.2 / 02.2T — Stage 2.** Keep exact evidence within its grounded offer passage or explicitly shared with the applicable offers. Check shared evidence across multiple offers, reject wrong-offer, fabricated, clipped, and ambiguous repeated quotes, and keep usable offers when another offer cannot be grounded. Fail extraction when the response claims offers and none can be grounded.
- **02.3 / 02.3T — Stages 1 and 2.** Exercise Arabic, English, and mixed sale and rent proposals. Include Arabic-Indic digits, written numbers, and the brief's price formats. Verify one request, typed normalized candidates, and bounded uncertainty and contradiction findings with source evidence where available. Assert that the prompt requests evidence-to-value verification before consistency assessment. Check that semantic interpretation is owned by the model and the validator only performs mechanical checks.
- **02.4 / 02.4T — Stage 2.** Cover malformed JSON and unusable envelopes with `invalid_extraction`, as well as invalid enums, types, numeric ranges, and formats in usable envelopes. Verify that a real quote paired with the wrong numeric value fails, including `3 BR` proposed as four bedrooms. Check clipped or signed quantities, location spans, Saudi mobile E.164, and price qualifiers. Preserve rejected originals and validation findings without dropping unrelated candidates or offers. Carry grounded semantic findings forward to the resolver and reviewer. Check arithmetic only for explicitly linked, verifiable operands.
- **02.5 / 02.5T — Stage 3.** Check null with no valid value, selection of one distinct value, collapse of identical values with evidence retained, and null on conflict or material uncertainty. Verify explicit SAR and supported rental periods. Compare complete asking-price tuples and keep deposits, installments, and unit rates separate. A linked arithmetic discrepancy clears amount and period, with operands retained. Exercise land and built area priorities, conflicts in the selected kind, and the agreement rule for other or unresolved types. Preserve nonselected area evidence. Keep location and contact grounded in explicit evidence.
- **02.5 / 02.5T — Stage 5.** Check stable reasons and `needs_review` for missing applicable fields, unresolved conflicts, material uncertainty, and invalid evidence that affects reliability. Check a complete listing, harmless rejection alongside a supported value, optional studio bedrooms, inapplicable land room counts, and other or unresolved property types. Verify mixed classification alone leaves the review status unaffected. Preserve the evidence behind each finding.
- **02.6 / 02.6T — Stages 0 and 6.** Exercise invalid JSONL and invalid raw input, with typed failures and zero gateway calls for those records. Verify typed provider failures propagate through the existing contract. Check the assembled public success schema before serialization, including `classification`, `detected_classes`, distinct application-assigned listing IDs, and `duplicate_of: null`. Run a mixed, multi-offer success and an invalid extraction followed by a success through the real CLI entry with a mocked gateway. Verify one ordered result per nonblank input line, clean JSONL stdout, continuation after failure, and exit 0 for all-success input or 1 for a batch with failures.

## 02.0 progress — 2026-11-09

The installed `agy` 1.5.3 authenticated and returned structured synthetic output. The original one-element Zod tuple emitted a draft-7 tuple schema rejected by the provider. The extraction schema now uses an equivalent array constrained to one element, and the provider accepted it. A synthetic CLI run with an explicitly injected experimental gateway returned a sale listing with `price.amount: 3200000` and review reasons for missing fields. This is an experiment, not a configured production entry point.

Offline gateway and extraction boundary checks passed 20 tests across three suites. Typecheck and build passed. The fake subprocess tests required execution outside the workspace sandbox to capture child output.

The `agy` schema error exposed model tool declarations. The CLI help provides no documented tool-free switch. The user requires a tool-less extraction call and specified that untrusted tool execution requires verified isolation. The experimental gateway was not wired into the production processor and was removed. This historical checkpoint was resolved by D-024, which selects the direct Gemini API without configured tools.
